## For Paul

Ordered most serious first. Items 1 to 4 can make a sentence in the published policy untrue; check them before this goes live.

1. **Where the data is stored: policy and repo disagree.** Section 5 says account, profile and game data is stored "in the **United States**". The repo says the production database is `(default)` in **europe-west2** (`docs/PRIZES_DEPLOY_CHECKLIST.md:9`; functions are europe-west2, `config/constants.ts:14`). I could find nothing in the repo that says US. The Storage bucket location is not documented anywhere I could read. The legacy `createWearCustomToken` is deliberately still deployed in us-central1 (`docs/engine-cutover-checklist.md:108-116`). I did NOT change section 5, because the evidence conflicts. A Firestore location can't be changed after creation, so the console shows the truth: `gcloud firestore databases describe --database='(default)' --project=ileadit-app` (read-only), and the bucket location under Storage. If the answer is London, section 5 and the transfers wording need rewriting (and the "standard contractual clauses" sentence may largely fall away).
2. **Backups and point-in-time recovery are not evidenced.** You asked me to reflect "backups kept up to 30 days, point-in-time recovery 7 days". There is no backup, PITR or backup-schedule configuration in `firebase.json`, the docs or the scripts (only Android `allowBackup=false`). The draft policy states it, because it matters for deletion (deleted data survives in backups until they age out). **Before publishing, confirm** with `gcloud firestore backups schedules list` and `gcloud firestore databases describe` (look for `pointInTimeRecoveryEnablement`). If it isn't set up, either set it up or remove those two sentences (section 6 table row "Backups" and section 7 "Backups" paragraph).
3. **Every automatic-deletion promise relies on a manual gcloud step.** The engine writes an expiry timestamp (`expireAt`) on day records, reports, claims and rate limits, but the Firestore TTL policy that actually deletes them is documented as a one-off command nobody has recorded running (`docs/FIRESTORE_SCHEMA.md:524-540`; `docs/moderation.md:32-33`). The policy says day records are "deleted automatically 30 days after..." and (new) reports "after 12 months". If TTL isn't enabled those statements are false. Check: `gcloud firestore fields ttls list --project=ileadit-app`.
4. **Anti-cheat flags can now hold a prize, which the policy denied.** Section 2 said checks "don't change your score or your account on their own". The engine now pauses a prize for admin review when a winner has flags (`services/prizeTrust.ts:1-62`). It never forfeits by itself ("over-holding is an admin look and never a forfeit"), and a person clears the hold. The draft adds an honest sentence. You should decide whether section 8's "no automated decisions with significant effects" line is still comfortable once prizes are live. Also: flag dates are kept for **400 days** (`services/trust.ts` `FLAG_HISTORY_DAYS`), not the "rolling 30 days" the table said. Flag kinds and dates only, never step counts. Draft corrects the row.
5. **Prizes: live or not?** The code is on main with no feature flag (`index.ts:27-30,55`), but `docs/PRIZES_DEPLOY_CHECKLIST.md` is entirely unticked, so I can't tell whether it is deployed. I drafted the prize wording so it is accurate once live. If prizes are not launching soon, you can drop that one bullet. The design collects no name, address, email or phone from winners (`callables/claimPrize.ts:1-12`); it stores `claimedAt`, optional `adultConfirmedAt`, `claimBy`. The organiser (creator) can read the claim record (`admin-web/firestore.rules:500-505`), so they can see that you claimed and confirmed 18+.
6. **App Check is not enforced in production, per `main`.** `functions/.env.ileadit-app` sets `ENFORCE_APP_CHECK=false`, labelled "deliberately temporary until Play Integrity ships" (committed 20 Sep). Play Integrity now ships in the app, but the override is still on main, and iOS says enforcement is not enabled (`AppCheckConfiguration.swift:9-12`). The policy table row "Firebase App Check ... Blocking fake apps and bots" is a claim about purpose; it is only true once enforcement is switched on. Not changed. Your call whether to soften.
7. **Push tokens are not removed on sign-out (both apps).** Android has no removal on sign-out (`NotificationRepository.removeInvalidToken` has no callers). iOS says in `DeviceTokenRegistrar.swift:11-12` that it deliberately does not. Tokens are only pruned when FCM reports them invalid, and when the account is deleted. So a phone can keep receiving a signed-out account's notifications (which can contain other players' display names), and a second person signing in on that phone can see them. The policy sentence ("until they stop working or you delete your account") is accurate, but this is a real privacy bug worth a ticket.
8. **Store declarations.**
   - **iOS `PrivacyInfo.xcprivacy` is missing "Other user content".** The optional 300-character report note is user content, and it is not declared (`ileadit/PrivacyInfo.xcprivacy:14-111`). Declared today: Fitness, Health, Name, Email, User ID, Photos, Device ID (push token), all linked / not tracking / App Functionality; Crash data unlinked. Please also check the App Store Connect label matches this.
   - **Play Data safety: I can't see the form.** From code, it should cover: health and fitness (steps, read-only, shared with nobody), name, email, user IDs, photos (profile photo), device ID (FCM token; Crashlytics installation ID), crash logs, plus the report note as user content. No analytics, no ads, no AD_ID. Android permissions at `origin/main`: INTERNET, ACCESS_NETWORK_STATE, CAMERA (optional), POST_NOTIFICATIONS, four Health Connect reads (steps, total steps, history, background), RECEIVE_BOOT_COMPLETED (`AndroidManifest.xml`). Android bug, not policy: `READ_HEALTH_DATA_IN_BACKGROUND` is declared in the manifest but missing from the `health_permissions` array in `res/values/arrays.xml`.
9. **Welcome-bonus hash wording.** Section 7 says the kept record "can't be turned back into your email address". The key is an unsalted SHA-256 of the lowercased email (`services/accounts.ts:29-31`), stored with the old account ID (`grants/{hash}`, never deleted by design, `services/deleteAccount.ts:69-72`). Anyone who already knows an email can test it against the hash, so it is pseudonymous, not anonymous. Not changed (legal call). Options: soften the sentence (iOS in-app copy already says "can't be used to identify or contact you"), or switch to a keyed hash (HMAC with a secret) in the engine.
10. **Deletion gaps (engine).** I found no handling for: competitions and invites you created (they keep `creatorId` / `createdBy` and an invite `label`); other players' block lists that contain your account ID; the reporter's note on a report about a deleted player (kept until the 12-month expiry). The policy now discloses the report note; it is silent on competitions you organise. Also the iOS in-app delete screen doesn't list photo, push tokens, reports or the legal record (the website policy does).
11. **Old date of birth and gender.** The policy says we don't collect them (true now). `functions/scripts/purgeDobGender.ts` exists to remove legacy values; I can't tell whether it was run. Worth confirming, since older accounts may still hold them.
12. **Claim to Fame is not in the policy.** It is opt-in (missing field means off). A weekly job writes `claims/{weekId}` (35-day TTL) and `private/game.ctfParticipation` holds your participation; it groups players by first name, town and avatar. iOS says "Only you see your trophies" and its delete screen mentions "your Claim to Fame entry". `COPY_DRAFT=false`; I can't tell whether it is live. I did not draft wording because the feature scope is outside this ticket. Decide whether it needs a paragraph before launch.
13. **Smaller notes.** Crashlytics is on by default with no opt-out on both apps (policy treats it as legitimate interest; fine, but it is a choice). Ops alerts go to Telegram, not Slack, and are built from an allowlist (job, kind, competition ID, counts): no personal data, so no processor entry is needed. Rate limiting on anonymous invite previews stores only an HMAC'd fragment of the IP, never the raw address. The 16+ rule is a checkbox; the server stores only `ageConfirmedAt`.

### Version bump needed? (`privacy-v2` unchanged in this PR)

**My recommendation: not for these corrections alone, but bundle a bump (`privacy-v3`) with the prizes launch. Your call.**

- Against bumping now: the new text mostly describes processing that already happens (reports, blocks, name filter, legal record, backups) or fixes wording. Nothing changes the health-data consent basis, adds a third party, or adds a new purpose for step data. The policy's own section 11 only promises an in-app notice and fresh consent for "new kinds of data or new uses".
- For bumping: prize claim records are a genuinely new kind of data once prizes switch on, and the prize hold (item 4) is a new use of the anti-cheat flags. Items 1 and 2 (location, backups) could also be judged material if they turn out to differ from what players read in v2.
- Mechanics if you bump: the version string is hard-coded in both apps (Android `legal/LegalConstants.kt:23`, iOS `LegalConfig.swift:20`), so it needs two app releases; the engine just stores whatever string it is sent (`services/legalAcceptance.ts`), and its header says a later version re-prompts acceptance. Existing accounts created before LEGAL-E1 have no acceptance record at all.
